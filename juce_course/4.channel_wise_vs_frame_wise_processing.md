
## The audio callback

In real-time audio processing
an **audio callback function** is repeatedly called.
Provided with a chunk of samples to process.

Processing in the callback must be completed in less time
than it takes to play back the given samples.

In JUCE, the **audio-callback** is handled by `processBlock()`
```cpp
void PluginProcessor::processBlock(juce::AudioBuffer<float>& buffer, juce::MidiBuffer&) {
	//
}
```

## `juce::AudioBuffer` class

The `AudioBuffer` class contains all the samples need to be processed
organizes as **"array of arrays"**

Each array holds the samples for a single audio channel.
A stereo buffer containing 480 frames will consist of two arrays.
Each array holding 480 samples (one for channel 0, one for channel 1)

`AudioBuffer` is a template class that works with `float` or `double`
representing a sample.

## Key Member Functions

`getNumSamples()` returns the number of _frames_ in the buffer
It refers to the frames rather than total individual samples across all channels.

`getNumChannels()` returns total number of channels in the buffer.

`getSample(int channel, int sampleIndex)` Retrieves the value of a single sample
at a specific channel at a specific location.

`getWritePointer(int channelNumber)` Returns a pointer to the first sample
in the given channel. 
Pointer can be treated as a C-style array using standard indexing operators.

`getArrayOfWritePointers()`: Returns an array of pointers
pointing to the individual channels in the buffer.
When templated to `float`
it returns a `float* const*`: 
A pointer to a constant array of arrays containing non-constant floats

## Processing Approaches
Samples are stored as an array of arrays.
You need two nested loops to iterate through them.

You can use modern c++20 functions `std::views:iota()`
to generate number ranges and simplify these index-based for-loops.

**two primary approaches**
### channel-wise processing
![[channel_wise.png]]
iterates over channels first, the over samples.
[[range_based_for_loops]]
[[views]]
```cpp
for (const auto channelIndex : std::views::iota(0, buffer.getNumChannels())){
	for (const auto sampleIndex : std::views::iota(0, buffer.getNumSamples())) {
		// process sample on (channelIndex, sampleIndex)
	}
}
```

**benefits**
High optimization: Processing samples within a single channel acts
on a continuous memoty block.
This enables advanced compiler performance optimization
**[Unrolling](https://komorinfo.com/en/blog/unroll-cpp-code-en/), and [vectorization](https://www.youtube.com/watch?v=VU8jSh5v5C8)** 
It also allows use of **SIMD (single-instruction-multiple-data) operations**
to process multiple samples with one processor instruction,
drastically increasing processing speed.

**challenges**
It complicates state management.

### Frame-wise processing
![[fra.png]]
This approach iterates over frames (time) first, and then over channels.
```cpp
for (const auto frameIndex : std::views::iota(0, buffer.getNumSamples())) {
	for (const auto channelIndex : std::views::iota(0, buffer.getNumChannels()))     {
	    // Apply processing/modulation to this sample
    }
}
```

**benefits**
**simpler state management**: Frame-wise processing is simpler.
By advancing frame by frame, it is trivial to update a shared state once per frame
and apply it evenly across all channels.

## Managing state LFO Dilemma
When implementing a shared state (An LFO generator for tremolo effect)
You must structure your code carefully based on chosen processing loop

If you must update your state every frame, follow these rules:
1. Use frame-wise processing if your state is shared across channels.
2. Duplicate the state per channel if you want to use channel-wise processing.
