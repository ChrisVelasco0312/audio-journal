# Real-Time Audio Programming & Plugin Processing Constraints

## 1. Overview of the Audio Processing Cycle

Audio plugins operate within a standard host execution cycle:

- `prepareToPlay()`: Initializes settings (e.g., sample rate, maximum block size) and allocates resources.
- `processBlock()`: The core audio callback invoked repeatedly to process buffers of audio samples.
- `releaseResources()`: Cleans up memory and resources when playback stops.

The plugin host calls `processBlock()` many times per second on a high-priority system thread known as the **audio thread**. To maintain continuous, glitch-free audio playback, every `processBlock()` call must finish processing its block of samples in significantly less time than the block's physical playback duration.

## 2. The Audio Pipeline & Latency

When an audio signal travels through a computer system, it traverses multiple software and hardware layers before reaching the output:

```
[Hardware / DAC] 
       ▲
       │ (System Audio Callback)
[Audio Device Driver]
       ▲
       │
[OS Kernel]
       ▲
       │
[Audio Driver API]
       ▲
       │
[Host Application / DAW]
       ▲
       │
[Plugin API / Glue Code]
       ▲
       │
[Plugin processBlock()]
```

### Trade-Offs & Constraints

- **Latency vs. Performance:**
    - Smaller buffer sizes reduce the delay (latency) between user input and audible output.
    - However, smaller buffers mean smaller deadlines for processing, leaving less time for CPU execution.
- **Real-World Impact:**
    - In live performance or real-time monitoring (e.g., playing an electric guitar through a distortion plugin), total round-trip latency must often remain below 8 ms.
    - Achieving sub-8 ms round-trip latency requires buffer sizes under 5 ms.
    - At a 48 kHz sample rate, a 240-frame buffer corresponds to 5 ms of audio. The plugin must complete its processing in a fraction of that 5 ms deadline.
- **Multi-Plugin Projects:** DAWs process dozens or hundreds of plugins sequentially or across processing graphs on the audio thread. The faster each individual plugin runs, the higher the total plugin capacity of the project before audio dropouts occur.
- **Audio Dropouts (Glitches):** If any plugin misses its deadline, the hardware buffer runs out of samples. This causes an audible glitch, which can damage hearing or hardware in high-volume or live environments.
    

## 3. Real-Time Programming Constraints

Audio programming operates under **near-real-time constraints** on consumer operating systems. Audio processing prioritizes **predictable, bounded worst-case execution time** over fast average-case performance.

### The Core Rules of `processBlock()`

#### 1. Do Not Allocate or Deallocate Memory

- **Forbidden:** `new`, `delete`, `malloc()`, `free()`, `std::make_unique`, `std::make_shared`, or mutating dynamic containers (e.g., `std::vector::push_back()`, copying non-fixed strings/vectors).
- **Reason:** OS memory management calls rely on heap allocators, which have non-deterministic completion times.
- **Solution:** Pre-allocate all required memory in `prepareToPlay()` or the constructor. Release memory in `releaseResources()` or the destructor.

#### 2. Do Not Acquire Mutexes or Locks

- **Forbidden:** `std::mutex`, `std::unique_lock`, or blocking synchronization primitives.
- **Reason:** Acquiring a lock introduces non-deterministic wait times and risk of priority inversion.
- **Solution:** Use lock-free or wait-free data structures. For primitive types (e.g., `float`), use `std::atomic<T>`. Verify lock-free status at compile time:
    
    C++
    ```
    static_assert(std::atomic<DataType>::is_always_lock_free);
    ```
    

For complex structures, use lock-free single-producer single-consumer (SPSC) FIFOs.

#### 3. Do Not Create or Wait on Threads

- **Forbidden:** Multithreading operations within `processBlock()`, thread spawning, or joining/waiting on worker threads.
- **Reason:** OS thread scheduling is non-deterministic. Multi-threaded average speedups (e.g., offloading via worker threads) do not guarantee deterministic completion within a single 5 ms window. Real-time audio processing within a single plugin block is inherently single-threaded.
- **Solution:** Offload heavy non-real-time background tasks to low-priority background threads and communicate via lock-free rings/queues.
    
#### 4. Do Not Perform File or Network I/O

- **Forbidden:** `std::cout`, file logging, disk reads/writes, network sockets.
- **Reason:** I/O operations rely on system calls and hardware access that can block execution unpredictably.
- **Solution:** Use background worker threads for disk streaming or logging, feeding buffers to the audio thread via lock-free FIFOs.
    
#### 5. Avoid Algorithms with Poor Worst-Case Complexity

- **Forbidden:** Algorithms with unbounded or spike-prone worst-case time complexity, even if their average performance is fast.
- **Reason:** A single missed deadline triggers an audible glitch.
- **Solution:** Benchmark and optimize explicitly for worst-case execution time.
#### 6. Avoid Non-Real-Time OS and Third-Party Calls

- **Forbidden:** System API functions or third-party libraries not explicitly documented as real-time safe.
- **Reason:** Undocumented system calls may internalize locks, allocations, or blocking operations.
- **Solution:** Stick strictly to deterministic arithmetic operations and real-time safe primitives.

## 4. Real-Time Rules Summary Table

|**Prohibited Operation**|**Primary Risk**|**Recommended Solution**|
|---|---|---|
|Dynamic Memory Allocation (`malloc`, `new`, vector resize)|Non-deterministic heap allocation latency|Pre-allocate in constructor or `prepareToPlay()`|
|Mutex Locks (`std::mutex`)|Priority inversion and unbounded wait times|Use `std::atomic` or lock-free SPSC queues|
|Multi-threading / Thread Waiting|OS thread scheduling delay|Keep processBlock single-threaded; offload tasks to background threads|
|File / Network I/O|Blocking I/O system calls|Double-buffering via background threads|
|Poor Worst-Case Algorithms|Transient CPU spikes causing dropouts|Select algorithms based on worst-case execution bounds|
