# JUCE Lesson 3.04: Channel-wise vs Frame-wise Processing

## Overview of the Audio Callback

In most real-time audio processing applications, an audio callback function is repeatedly called and provided with a chunk of samples to process [cite: 1]. The processing within this callback must be completed in less time than it takes to play back the given samples [cite: 1].

In JUCE plugins, this audio callback is handled by the `processBlock()` function [cite: 1]. The function signature typically looks like this:

```cpp
void PluginProcessor::processBlock(juce::AudioBuffer<float>& buffer, juce::MidiBuffer&) {
    // ...
}
```

[cite: 2]

## The `juce::AudioBuffer` Class

The `AudioBuffer` class contains all the samples that need to be processed, organized as an "array of arrays" [cite: 1]. Each array within the buffer holds the samples for a single audio channel [cite: 1]. For example, a stereo buffer containing 480 frames will consist of two arrays, with each array holding 480 samples (one for channel 0, one for channel 1) [cite: 1, 2].

The `AudioBuffer` is a template class that works with either `float` or `double` data types representing a sample [cite: 1, 2]. In this specific course, `float` is utilized [cite: 1, 2].

### Key Member Functions

- **`getNumSamples()`**: Returns the number of _frames_ in the buffer [cite: 1, 2]. Note that this naming can be inaccurate and confusing, as it refers to frames rather than total individual samples across all channels [cite: 1].
- **`getNumChannels()`**: Returns the total number of channels present in the buffer [cite: 1, 2].
- **`getSample(int channel, int sampleIndex)`**: Retrieves the value of a single sample at a specific channel and index location [cite: 1, 2].
- **`setSample(int destChannel, int destSample, float newValue)`**: Sets the value of a single sample at a specific location [cite: 1, 2].
- **`getWritePointer(int channelNumber)`**: Returns a pointer to the first sample in the given channel [cite: 1, 2]. This pointer can be treated as a C-style array using standard indexing operators [cite: 1].
- **`getArrayOfWritePointers()`**: Returns an array of pointers pointing to the individual channels in the buffer [cite: 1, 2]. When templated to `float`, this returns a `float* const*` (a pointer to a constant array of arrays containing non-constant floats) [cite: 1, 2].

## Processing Approaches

Since samples are stored as an array of arrays, you need two nested loops to iterate through them [cite: 1]. You can use modern C++20 functions like `std::views::iota()` to easily generate number ranges and simplify these index-based for-loops [cite: 1, 2].

This leads to two primary approaches for audio processing:

### 1. Channel-Wise Processing

This approach iterates over channels first, and then over samples [cite: 1].

```cpp
for (const auto channelIndex : std::views::iota(0, buffer.getNumChannels())) {
    for (const auto sampleIndex : std::views::iota(0, buffer.getNumSamples())) {
        // Process sample on (channelIndex, sampleIndex)
    }
}
```

[cite: 2]

**Benefits:**

- **High Optimization Potential**: Processing samples within a single channel acts on a continuous memory block [cite: 1]. This enables advanced compiler performance optimizations, loop unrolling, and vectorization [cite: 1, 2]. It also allows the use of SIMD (single-instruction multiple-data) operations to process multiple samples with one processor instruction, drastically increasing processing speed [cite: 1, 2].

**Challenges:**

- It complicates state management [cite: 1]. If an effect relies on a shared state (like an LFO for a tremolo effect modulating all channels), using channel-wise processing makes it difficult to correctly reset or track the LFO state per channel, often resulting in bugs [cite: 1].

### 2. Frame-Wise Processing

This approach iterates over frames (time) first, and then over channels [cite: 1].

```cpp
for (const auto frameIndex : std::views::iota(0, buffer.getNumSamples())) {
    // Retrieve LFO value for this frame here
    for (const auto channelIndex : std::views::iota(0, buffer.getNumChannels())) {
        // Apply processing/modulation to this sample in the frame
    }
}
```

[cite: 2]

**Benefits:**

- **Simpler State Management**: Frame-wise processing is much simpler to get right, especially for beginners [cite: 1, 2]. By advancing frame by frame, it is trivial to update a shared state (like retrieving the next LFO value) once per frame and apply it evenly across all channels [cite: 1, 2].

## Managing State: The LFO Dilemma

When implementing a shared state (such as an LFO generator for a tremolo effect), you must structure your code carefully based on your chosen processing loop.

If you must update your state every frame, follow these rules:

1.  **Use frame-wise processing** if your state is shared across channels [cite: 1, 2].
2.  **Duplicate the state** per channel if you want to use channel-wise processing [cite: 1, 2].

If you insist on using **channel-wise processing** for a shared LFO, you can pre-generate the LFO values for the entire block using a helper buffer [cite: 1, 2]. You would write all LFO values into this helper buffer before your main channel-loop begins, and then simply read from the helper buffer during sample processing [cite: 1, 2]. Note that this approach inherently increases memory usage [cite: 1].

## Summary & Recommendations

- Start by using **frame-wise processing**, as it is simpler and prevents common bugs associated with sharing state across channels [cite: 1, 2]. The tremolo plugin built in this course uses the frame-wise approach [cite: 1, 2].
- Once comfortable, and if profiling shows a need for efficiency, switch to **channel-wise processing** to leverage performance optimizations like SIMD [cite: 1, 2].
