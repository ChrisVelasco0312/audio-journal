
### Plugin processor cycle
![[plugin_processor_cycle.png]]
`prepareToPlay()` 
	initialized settings (sample rate, maximum block size)
	 Allocate resources
`processBlock()`
	 Core audio callbak invoked repeatedly to process buffers.
`releaseResources()`
	 Cleans up memory and resources when playback stops

Host calls `processBlock()` multiple times per second
in a high-priority system known as **audio thread**

To mantain continuous free audio playback.
every `processBlock()` call must finish processing in less time
than the block's physical playback duration.

## Audio pipeline and latency

An audio signal traverses multiple software and hardware layers.
![[audio_stack.png]]
#### trade-offs and constraints
**latency vs performance**
	Smaller buffer sizes reduce the **delay(latency)** between
	user input and audible output
	Smaller buffers means smaller **deadlines** for processing
	leaving less time for **CPU** execution
**real world impact**
	 - In live performance or real-time monitoring,
	 [[total round-trip latency]] must oftern remain below 8 ms.
	 - Achiving sub-8 ms round-tip latency must often remain below 8 ms.
	 - At 48 kHz sample rate, a 240-frame buffer corresponds to 5 ms of audio.
	 the plugin must complete its processing in a fraction of that 5ms deadline.
**Multi-Plugin Projects**
	DAWs process dozend or hundreds of plugins sequentially.
	 The faster each individual plugin runs, the higher the total plugin capacity
	 of the project before audio dropouts occur.
**Audio Dropouts**: 
	 If any plugin misses its deadline
	 hardware buffer runs out of samples.
	 The glitch is audible, can damage heareing or hardware.
## Real time programming constraints

Audio programming operates under **near-real-time constraints**.
Audio processing prioritize:
	**Predictable, bounded worst-case execution time**
	Over fast average-case performance


### Core rules of processBlock()

**Do not allocate or deallocate memory**
**Forbidden**: `new`, `delete`, `malloc()`, `free()`, `std::make_unique`, std::make_shared, or
mutating dynamic containers `std::vector::push_back()`
copying non-fixed string/vectors
**Reason**: OS memory management calls rely on **heap allocators**
which have **non-deterministic completion times**.
**Solution**: Pre-allocate all required memory in `prepareToPlay()` or **constructor**
Release memory in `releaseResources()` or the **destructor**

### Do not acquire mutexes or locks
**Forbidden**: `std::mutex`, `std::unique_lock` or blocking synchronization primitives.
**Reason** Acquiring a lock instroduces non-deterministic wait times
**risk of priority inversion**
**Solution** USe lock-free or wait-free data strcutures,
For primitive types like `float` use `std::atomic<T>`
Verify lock-free status at compile time
```c++
static_assert(std::atomic<DataType>::is_always_lock_free);
```

For complex structures use lock-free **single-producer** 
**single-consumer (SPSC) FIFOs** 

### Do not create or wait on threads.
**forbidden** multithreading operations within `processBlock()`
thread spawning, or joining/waiting on worker threads.
**reason** OS thread scheduling is non-deterministic.
Multi-threaded average speddups do not guarantee deterministic completion
within 5ms window.
Real time audio processing within a single plugin block is single threaded.
**solution** offload heavy non-real-time background tasks to **low-priority background**
**threads** and communicate vial **lock-free rings/queues.**

### Do not perform File or Network I/O
**forbidden** `std::cout`, dile logging, disk reads/writes, network sockets.
**reason** I/O operations rely on system calls and hardware acces that can block execution.
**solution** Use background worker threads for disk streaming or logging
feeding buffers to the audio thread via **lock-free FIFOs**

### Avoid Algoriths with Poor Worst-Case complexity
**forbidden**: Algorithms with unbounded or spike-prone worst-case time complexity.
**reason** A single missed deadline triggers a glitch.
**solution** Benchmark and optimize explicitly for worst-case execution time.

### Avoid non-real-time OS and Third Party calls
**forbidden** System API functions or third-part libraries not prepared for real time safe.
**reason** Undocumented system calls may internalize locks, allocations, blocking ops
**solution** Stick with deterministic arithmetic ops, real-time safe primitives
