When the host app need new audio from plug-in
it will call `processBlock()`
This is the **audio callback**

The audio stream is chopped up into smaller portions **blocks**
A block can be as small as 16 samples or 4096 samples.

If is 128 at 44.1kHz `processBlock()` 
is called 44100/128 = 344.53 times per second

The smaller the size of the block, the more often the host needs
to send the `processBlock()` command

if block size is too small, computer will stutter
the larger the block is, the longer the delay
that delay is known as **latency**

Mos DAWs call the block size as the **buffer size**

At sample rate of 44.1 kHz a buffer of 256 samples
has 5.8 milliseconds latency while a buffer of 1024 has 23.2

Even if the user configures buffer size in DAW
size of the block isn't necesarily the same from one invocation to the next.
DAW my decide to call `processBlock` with smaller block size.
The host **buffer size** is the maximum number of samples

## don't miss deadline!

A common cause of glitches is the plug-in being unable to meet deadline.

Two things that can cause `processBlock` to miss its deadline
**buffer size is too small** 
**audio thread** was temporarily **halted**
there is not enough time left to process the reamaining samples.

The plug-in will run on the computer's CPU
Modern CPUs have multiple cores
the can run several programs at the same time (mutitasking)
They can run using separate **threads** of execution (multithreading)

The audio processing logic `processBlock`
runs in its own thread **audio thread**
Is a high priority thread.

It is essential that plug-in audio callback never pauses the thread it's runnning on
memory allocation and system calls are **forbidden** in `processBlock`

There are other threads of execution in the plug-in
User Intergace is handled by lower priorit **UI Thread**
or main thread, or JUCE parlance, the message thead.

**UI Thread** doesn't have strict deadlines like audio thread
but plug-in has to communicate between these two
when using parameters exposed in the interface

Most standard ways to communicate between threads involve putting
one of the threads to sleep for a short while using a **lock** or **mutex**

Sleeping isn't allowed in audio code
for audio there are special communication mechanism that avoid locks.
